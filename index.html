01. 문제 정의

어떤 문제를 해결하는가?

"만들고 싶어서"가 아니라
"이런 문제가 있어서" 만들어야 한다.

타겟 사용자

😥 자신의 진로를 명확히 탐색하지 못한 사용자가
본인의 경험 및 흥미를 비정형적으로 작성하면,
그걸 바탕으로 맞춤형 채용 공고를 추천해주는 시스템

핵심 문제

  • 공공기관 채용공고는 ALIO에 분산 등록 — 개인 모니터링 불가
  • 자신의 경험을 어떤 직무와 연결해야 할지 모름
  • 이력서/경험은 비정형 텍스트 — 자동 분석이 어려움
  • 공고마다 직무 요건이 달라 일대일 비교가 어려움

솔루션 방향

01. 문제 정의

5Whys — 진짜 문제 찾기

인식된 문제 → 5번의 Why → 진짜 문제 정의
W1
왜 사용자가 자신에게 맞는 공고를 찾지 못하는가?
자신의 경험/흥미를 어떤 직무와 연결해야 할지 모르기 때문이다
W2
왜 경험-직무 연결이 어려운가?
사용자의 경험은 비정형 텍스트이고, 공고의 직무 요건은 각기 다른 형식으로 작성되어 있다
W3
왜 자동으로 분석해줄 시스템이 없는가?
채용공고 데이터와 사용자 경험을 연결하는 구조화된 매칭 시스템이 존재하지 않는다
W4
왜 매칭 시스템을 만들기 어려운가?
공고는 기관별로 제각각 — 통합 분류 체계(NCS, 지역, 학력 등)로 정규화해야 하며, 사용자 경험도 같은 체계로 분석해야 하기 때문이다
W5
진짜 문제는?
"진로를 탐색 중인 사용자의 비정형 경험을 분석하여,
구조화된 채용 데이터와 자동으로 매칭하는 시스템이 필요하다"
👉 진짜 문제 정의문
"자신의 진로를 명확히 탐색하지 못한 사용자가 본인의 경험 및 흥미를 비정형적으로 작성하면,
그걸 바탕으로 맞춤형 채용 공고를 추천해주는 시스템을 개발하자"

⭐ 03. 구현 과정 — 핵심

아키텍처 진화: CrewAI → 경량화

"결과물이 아니라,
결과물을 만들어가는 과정이 중요하다"
🔴 Phase 1
CrewAI 프레임워크 기반
초기에는 CrewAI의 Multi-Agent 구조 도입 → 과도한 추상화, 응답 속도 저하, 디버깅 어려움 발생
교훈: "Over-engineering은 오히려 독이다. 단순한 문제에 복잡한 프레임워크가 필요하지 않다"
🟡 Phase 2
CrewAI 제거 → 자체 LLM 클라이언트
CrewAI 의존성 완전 제거 → llm_client.py 자체 구현
✅ Input Token 60% 절감 (온톨로지 키워드 15개 제한, 텍스트 청크 800자)
✅ Groq 폴백 모델 6개로 확장 (장애 대응)
✅ server.py 범용화 (OS/환경 독립적 실행)
🟢 Phase 3
안정화 + 자동화
GitHub Actions CI/CD 구축 → 매주 월요일 09:00 KST 자동 수집
프론트엔드 복구, main_batch.py 복원
지속적 운영 중 (24주+)
CrewAI → 자체 LLM Client → 60% Token 절감

Q. 왜 CrewAI를 버렸나요?
A. Over-engineering이었습니다. 단순한 파이프라인에 Multi-Agent 프레임워크는 불필요한 복잡성을 추가했습니다. 자체 LLM 클라이언트로 교체 후 Token 60%를 절감했고, 디버깅이 훨씬 쉬워졌습니다.
Q. 기존 채용 플랫폼과의 차별점은?
A. 단순 키워드 검색이 아닌, ALIO API 원문 데이터를 NCS 기반 온톨로지로 구조화하여 공고 간 관계까지 분석합니다. Obsidian Wiki를 통한 지식 그래프 연결이 핵심입니다.
Q. 가장 어려웠던 점은?
A. 초기에 '완벽한' 아키텍처를 고집하다 시간을 낭비한 점입니다. 이후 "일단 동작하는 최소 버전(MVP)"을 먼저 만들고 점진적으로 개선하는 방식으로 전환하면서 프로젝트가 탄력을 받았습니다.
Q. 이 프로젝트를 통해 배운 점은?
A. 공학 설계에서 가장 중요한 것은 "문제를 정확히 정의하는 것"과 "과정에서 배우는 것"입니다. 처음에 5Whys로 진짜 문제를 찾아낸 과정과, CrewAI 실패에서 배운 교훈이 가장 값진 경험이었습니다.
