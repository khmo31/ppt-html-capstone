## 예상 Q&A

### Q. 왜 CrewAI를 버렸나요?
Over-engineering이었습니다. 단순한 파이프라인에 Multi-Agent 프레임워크는 불필요한 복잡성을 추가했습니다. 자체 LLM 클라이언트로 교체 후 Token 60%를 절감했고, 디버깅이 훨씬 쉬워졌습니다.

### Q. 기존 채용 플랫폼과의 차별점은?
단순 키워드 검색이 아닌, ALIO API 원문 데이터를 NCS 기반 온톨로지로 구조화하여 공고 간 관계까지 분석합니다. Facet Wiki를 통한 지식 그래프 연결이 핵심입니다.

### Q. 가장 어려웠던 점은?
초기에 '완벽한' 아키텍처를 고집하다 시간을 낭비한 점입니다. 이후 "일단 동작하는 최소 버전(MVP)"을 먼저 만들고 점진적으로 개선하는 방식으로 전환하면서 프로젝트가 탄력을 받았습니다.

### Q. 이 프로젝트를 통해 배운 점은?
공학 설계에서 가장 중요한 것은 "문제를 정확히 정의하는 것"과 "과정에서 배우는 것"입니다. 처음에 5Whys로 진짜 문제를 찾아낸 과정과, CrewAI 실패에서 배운 교훈이 가장 값진 경험이었습니다.

### Q. 왜 임베딩(Vector DB)을 포기하고 Wiki 방식으로 전환했나요?
임베딩은 "의료기기 연구개발"과 "의공학"의 관계가 왜 연결되는지 설명하지 못합니다. 반면 NCS 분류 체계 기반 Wiki는 "보건의료"라는 공통 분류를 통해 관계를 설명할 수 있어, 사용자에게 더 투명한 매칭 결과를 제공할 수 있습니다.

### Q. 단일 LLM만 사용하는 이유는?
OpenCode Go API를 주력으로 사용하고, 장애 상황에서만 Groq로 폴백합니다. 단일 모델을 사용하면 응답 일관성이 유지되고, API 비용 예측이 가능합니다. Groq는 무료이므로 폴백 시에도 비용 부담이 없습니다.

### Q. 향후 확장 계획이 있나요?
현재는 공공기관(ALIO)에 한정되어 있지만, 사람인·잡코리아 등 사기업 채용정보 API를 추가로 연동하여 공공+민간 통합 채용 매칭 플랫폼으로 확장할 계획입니다. 또한 Vector DB와 Wiki를 결합한 하이브리드 검색도 고려 중입니다.

### Q. 3인 팀인데 역할 분담은 어떻게 했나요?
백엔드(강현모)가 전체 파이프라인과 매칭 엔진을, 프론트엔드(양병현)가 웹 UI를, QA(권오규)가 테스트와 데이터 품질을 담당했습니다. 각 모듈을 독립적으로 설계하여 역할 간 의존성을 최소화했습니다.
